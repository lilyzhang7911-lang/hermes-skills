# 执行前检查清单

## 何时使用

在执行任何涉及以下操作的任务前，必须过一遍此清单：
- 文件创建/修改/删除
- 代码生成/重构
- 配置变更
- 批量操作
- 视觉/格式相关任务

## 5 类失败模式与预防

### 1. 验证不充分（抽样代替全量）

**失败案例**：PPTX 改色只抽样 1 页，结果 12 页标题白字看不见。

**预防**：
```
□ 验证方案是全量的还是抽样的？
  - 批量操作 → 必须遍历全部元素
  - 视觉修改 → 必须全量对比度/可见性校验
  - 文本修改 → 必须全量内容校验
□ 能否用程序化方式验证？（优先程序化，而非人工抽样）
```

### 2. 事实源漂移（假设=历史快照）

**失败案例**：假设 PPTX 文件=脚本输出，实际已被手动大改。

**预防**：
```
□ 事实源的当前状态是什么？
  - 配置文件 → 先读当前值，不要假设等于默认值
  - 数据库 → 先查当前记录，不要假设等于上次看到的
  - 代码/文件 → 先 git diff 或直接读取，不要假设等于上次 commit
□ 是否需要先核实事实源再动手？
```

### 3. 能力边界误判（直觉代替量化）

**失败案例**：公式字号压到 11pt，严重失真。

**预防**：
```
□ 工具/模型的能力边界是什么？
  - 模型输出长度 → 查实测记录
  - 工具渲染极限 → 查实测记录
  - 网络超时阈值 → 查实测记录
□ 是否有量化记录？还是凭"应该可以"的直觉？
```

### 4. 分工判断缺失（agent 抢先做用户更快的事）

**失败案例**：agent 用 curl 下载 GitHub 文件，用户浏览器下载更快。

**预防**：
```
□ 这件事用户手动做是否更快？
  - 浏览器下载 → L1 必问（给选择题）
  - 拖拽/移动文件 → L1 必问
  - 简单配置修改（改个字段） → L1 必问
  - 批量操作（改 10+ 文件） → agent 做
  - 需要技术知识的操作 → agent 做
□ 不确定时 → 问一句"这个你要自己下载还是我来？"
```

### 5. 中间产物替代最终效果

**失败案例**：用"OMML 节点数不变"作为"改色成功"的判据。

**预防**：
```
□ 验证的是最终效果还是中间产物？
  - 代码重构 → 验证行为不变（测试通过），不是 AST 节点数不变
  - 数据库迁移 → 验证业务查询结果，不是行数不变
  - UI 修改 → 验证视觉效果，不是 DOM 节点数不变
□ 最终用户可感知的效果是什么？
```

## 执行前必过清单（快速版）

```
1. 分工判断：这件事用户手动做是否更快？→ 给选择题
2. 事实源核实：当前状态是什么？→ 先读/查
3. 能力边界：工具/模型的极限是什么？→ 查记录
4. 验证方案：全量还是抽样？→ 必须全量
5. 验证目标：最终效果还是中间产物？→ 必须最终效果
```

## 因果链（根因分析）

这 5 类失败构成因果链：

```
分工判断缺失（类型 4）
  → 没有给用户确认的机会
  → 直接执行
  → 事实源漂移（类型 2，因为没核实）
  → 能力边界误判（类型 3，因为没量化）
  → 验证不充分（类型 1，因为赶时间）
  → 中间产物替代最终效果（类型 5，因为偷懒）
```

**根因在类型 4（分工判断）和类型 2（事实源漂移）**——如果在一开始就核实事实源、给用户确认机会，后续的失败都可以避免。

## 哲学映射

用黑格尔的术语：

- **类型 1/5** 是知性的懒惰——停留在"部分=整体"的知性判断，没有上升到理性的具体普遍性
- **类型 2** 是知性的固执——把"过去的概念"当作"当前的实在"，没有把握概念的自我运动
- **类型 3** 是知性的自负——以为"应该可以"就够了，不愿意用经验来检验概念
- **类型 4** 是主体性的缺失——没有把用户作为另一个主体来承认，而是当作被动的观察者

**真正的自我修复，不是"下次注意"，而是把这 5 类失败内化为认知结构的一部分——让"全量验证"成为像呼吸一样自然的环节。**
