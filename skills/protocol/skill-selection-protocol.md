# Skill Selection Protocol

## 触发条件

以下任一条件成立时，**必须**先出提案，后执行：

1. 任务需要 **≥2 个不同 skills/tools** 组合完成
2. 任务存在 **多种可行路径**，需要显式比较
3. 用户明确要求 **复杂任务** 或 **深度思考**

## 豁免条件

以下情况**不必**走协议：

- 单步操作（如“读取这个文件”）
- 单一工具调用（如“搜索这个关键词”）
- 无歧义指令（如“删除这个文件”）

## 提案格式

所有提案必须包含以下结构：

```
## 提案：{任务标题}

### Selected（选中方案）
| 方案 | 理由 |
|------|------|
| 方案A | 具体原因 |

### Skipped（跳过方案）
| 方案 | 排除理由 |
|------|----------|
| 方案B | 具体排除原因 |

### Gaps（缺口与补充建议）
- 缺口1 + 补充建议
- 缺口2 + 补充建议

⏳ 请确认，或直接修改此提案
```

## 执行纪律

1. **提案未确认前，不做任何有副作用操作**
2. 确认后，按提案执行，不擅自变更方案
3. 执行过程中若遇到新分支，**暂停并补充提案**，等待二次确认
4. 关键选择点必须在 session 历史中留痕

## 验收标准

- **触发准确**：复杂任务100%走协议，简单任务不滥用
- **提案质量**：用户无需追问即可做出决策
- **执行纪律**：未确认不执行，确认后不偏离
- **证据留痕**：关键决策可回溯到具体 session 消息

## 与相关 Skills 的关系

- 与 `grilling` 配合使用：在需求理解阶段用 grilling 澄清，在方案选择阶段用本协议呈现
- 与 `to-tickets` 配合使用：提案确认后，拆解为可执行 tickets
- 与 `handoff` 配合使用：复杂任务的中间状态通过 handoff 文档固化
