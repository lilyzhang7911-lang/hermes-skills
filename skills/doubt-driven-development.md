# 怀疑驱动开发 (Doubt-Driven Development)

## 概述

自信的答案不等于正确的答案。长会话会积累上下文，使假设悄然变成"事实"而不被察觉。怀疑驱动开发是一种纪律：在任何非平凡输出生效之前，引入一个以**证伪**为导向的新鲜上下文审查者。

这不是 `/review`（后者是对已完成制品的裁决）。这是在途姿态——非平凡决策在修正成本仍低时被交叉质询。

## 触发条件

当以下任一条件为真时，决策是**非平凡的**：
- 引入或修改分支逻辑
- 跨越模块或服务边界
- 断言类型系统/编译器无法验证的属性（线程安全、幂等性、顺序、不变量）
- 正确性依赖于未来读者看不到的上下文
- 影响范围不可逆（生产部署、数据迁移、公开 API 变更）

**不适用场景：** 机械操作（重命名、格式化）、明确的用户指令、读取/总结现有代码、一行明显正确的变更。

## 流程 (CLAIM → EXTRACT → DOUBT → RECONCILE → STOP)

```
怀疑循环:
- [ ] Step 1: CLAIM — 写出声明 + 为什么重要
- [ ] Step 2: EXTRACT — 隔离制品 + 契约，剥离推理
- [ ] Step 3: DOUBT — 调用新鲜上下文审查者（对抗性提示）
- [ ] Step 4: RECONCILE — 将每个发现与制品文本对照分类
- [ ] Step 5: STOP — 满足停止条件（平凡发现、3 轮循环、或用户覆盖）
```

### Step 1: CLAIM — 浮现声明

用两三行命名决策：
```
CLAIM: "新的缓存层在规格描述的读密集负载下是线程安全的。"
WHY THIS MATTERS: 这里的竞态会污染用户数据且难以在 QA 中检测。
```
如果无法紧凑地写出声明，说明你有的只是感觉而非决策——先浮现它再审查。

### Step 2: EXTRACT — 最小可审查单元

新鲜上下文审查者需要**制品**和**契约**，不需要你的推理过程。
- 代码：diff 或函数——不是整个文件
- 决策：3-5 句提案 + 必须满足的约束
- 断言：声明 + 支撑证据（与 Step 1 的 CLAIM 块区分）

剥离你的推理。如果交出结论，你会得到结论的验证。制品必须小到审查者一次阅读就能掌握——如果是 500 行 PR，先分解。

### Step 3: DOUBT — 调用新鲜上下文审查者

提示**必须是对抗性的**。框架决定答案。
```
对抗性审查。找出这个制品的问题。
假设作者是过度自信的。寻找：
- 未声明的假设
- 未处理的边界情况
- 隐藏的耦合或共享状态
- 契约可能被违反的方式
- 可能破坏的现有约定
- 意外输入下的故障模式

不要验证。不要总结。找出问题，或在彻底检查后明确说明找不到任何问题。

ARTIFACT: <粘贴制品>
CONTRACT: <粘贴契约>
```

**只传递 ARTIFACT + CONTRACT。不传递 CLAIM。** 交出结论会偏向同意。

#### 跨模型升级（可选）

单一模型审查者与原始作者共享盲点——更冷、不同架构的模型能捕捉它们。
- 交互会话：**必须提供**。在 Step 3 后、RECONCILE 前暂停询问用户。
- 非交互上下文（CI/定时任务）：跳过并声明"跨模型跳过：非交互上下文"。

### Step 4: RECONCILE — 折叠发现

审查者的输出是数据，不是裁决。**你仍是编排者。** 在分类前重读制品文本—— rubber-stamping 与忽略是同样的失败模式。

按**优先级顺序**分类每个发现：
1. **契约误读** — 审查者标记是因为 CONTRACT 不清楚或不完整。先修复契约，下次循环重新分类。
2. **有效 + 可操作** — 需要修改制品的真实问题。修改它，重新循环。
3. **有效权衡** — 问题是真实的但修复成本超过接受成本。明确记录权衡供用户决策。
4. **噪音** — 审查者标记的实际上是正确的（缺少上下文）。注明，继续，并问：将那个上下文加入契约能否防止误报？

### Step 5: STOP — 有界循环

满足以下任一条件停止：
- 下一次迭代只返回平凡或已考虑过的发现
- 完成 3 轮循环（升级到用户，不独自磨第四轮）
- 用户明确说"交付吧"

如果 3 轮后仍有实质性发现，制品可能未准备好——向用户报告。

## 反合理化表

| 合理化 | 现实 |
|---|---|
| "我很自信，跳过怀疑步骤" | 自信与正确性相关性差。确定时刻恰恰是盲点隐藏之处。 |
| "调用审查者太贵" | 在生产中调试错误提交比有界的检查更昂贵。 |
| "审查者只会挑刺" | 只有未限定范围时才会。将提示约束为"契约下会导致失败的问题"。 |
| "我会在最后用 `/review` 做怀疑" | `/review` 是最终门控。怀疑驱动在方向错误时早期捕获，PR 时已太晚。 |
| "如果每一步都怀疑就永远无法交付" | 该技能仅适用于非平凡决策，不是每个按键。重读"何时不适用"。 |

## 红旗

- 对一行重命名或格式化调用新鲜上下文审查者
- 不经重读制品文本就将审查者输出视为权威
- 不升级用户就循环 >3 轮
- 用"这个好吗？"提示审查者而非"找出问题"
- 在高 stakes 决策的时间压力下跳过怀疑
- 只在提交后怀疑——那是 `/review`，不是怀疑驱动开发

## 验证

- [ ] 每个非平凡决策都明确命名为 CLAIM
- [ ] 至少一个新鲜上下文审查（TDD RED 步骤产生的失败测试满足行为声明）
- [ ] 审查者收到 ARTIFACT + CONTRACT —— 不是 CLAIM，不是推理
- [ ] 提示是对抗性的（"找出问题"），不是验证性的（"这个好吗"）
- [ ] 发现按制品文本分类（非 rubber-stamp）
- [ ] 满足停止条件
- [ ] 交互模式下跨模型被明确提供
