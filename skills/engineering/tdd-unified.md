# 测试驱动开发 (TDD) 统一指南

统一入口：覆盖 TDD 方法论、接缝测试、工作流编排、反模式防护。

## 场景决策树

```
开始
├─ 需要理解 TDD 核心原则？ → 方法论
├─ 需要确定测试位置？ → 接缝测试
├─ 需要编排 Agent 执行 TDD？ → 工作流
└─ 需要避免常见错误？ → 反模式
```

## 一、TDD 方法论

### 核心原则

**铁律：没有失败的测试，不写生产代码。**

如果你没有看到测试失败，你不知道它是否测试了正确的东西。

**违反规则的字面意思就是违反规则的精神。**

### 何时使用

**总是：**
- 新功能
- Bug 修复
- 重构
- 行为变更

**例外（先问用户）：**
- 一次性原型
- 生成的代码
- 配置文件

想着"就这一次跳过 TDD"？停下。那是合理化。

### RED-GREEN-REFACTOR 循环

#### RED — 写失败测试

写一个最小的测试，展示应该发生什么。

**好测试：**
```python
def test_retries_failed_operations_3_times():
    attempts = 0
    def operation():
        nonlocal attempts
        attempts += 1
        if attempts < 3:
            raise Exception('fail')
        return 'success'

    result = retry_operation(operation)

    assert result == 'success'
    assert attempts == 3
```
清晰的名称，测试真实行为，一件事。

**坏测试：**
```python
def test_retry_works():
    mock = MagicMock()
    mock.side_effect = [Exception(), Exception(), 'success']
    result = retry_operation(mock)
    assert result == 'success'  # 重试次数呢？时序呢？
```
模糊的名称，测试 mock 而不是真实代码。

**要求：**
- 每个测试一个行为
- 清晰的描述性名称（名称中有"and"？拆分它）
- 真实代码，不是 mocks（除非真正不可避免）
- 名称描述行为，不是实现

#### 验证 RED — 看它失败

**强制。永不跳过。**

```bash
# 使用 terminal 工具运行特定测试
pytest tests/test_feature.py::test_specific_behavior -v
```

确认：
- 测试失败（不是因为拼写错误的错误）
- 失败消息是预期的
- 因为功能缺失而失败

**测试立即通过？** 你在测试现有行为。修复测试。

**测试出错？** 修复错误，重新运行直到它正确失败。

#### GREEN — 最小代码

写最简单的代码通过测试。没有更多。

**好：**
```python
def add(a, b):
    return a + b  # 没有额外
```

**坏：**
```python
def add(a, b):
    result = a + b
    logging.info(f"Adding {a} + {b} = {result}")  # 额外！
    return result
```

不要添加功能、重构其他代码，或"改进"超出测试。

**GREEN 中作弊可以：**
- 硬编码返回值
- 复制粘贴
- 重复代码
- 跳过边界情况

我们会在 REFACTOR 中修复它。

#### 验证 GREEN — 看它通过

**强制。**

```bash
# 运行特定测试
pytest tests/test_feature.py::test_specific_behavior -v

# 然后运行所有测试检查回归
pytest tests/ -q
```

确认：
- 测试通过
- 其他测试仍然通过
- 输出干净（没有错误、警告）

**测试失败？** 修复代码，不是测试。

**其他测试失败？** 现在修复回归。

#### REFACTOR — 清理

只在绿色之后：
- 移除重复
- 改进名称
- 提取助手
- 简化表达式

在整个过程中保持测试绿色。不要添加行为。

**如果重构期间测试失败：** 立即撤销。采取更小的步骤。

#### 重复

下一个行为的下一个失败测试。一次一个循环。

### 避免水平切片

**不要**先写所有测试然后所有实现。那是水平切片：RED 变成"写一堆想象的测试"，GREEN 变成"让这堆通过。"它产生脆弱的测试，因为测试是在实现教你什么行为和界面真正重要之前设计的。

使用垂直示踪弹代替：

```
错误：
  RED:   test1, test2, test3, test4
  GREEN: impl1, impl2, impl3, impl4

正确：
  RED→GREEN: test1→impl1
  RED→GREEN: test2→impl2
  RED→GREEN: test3→impl3
```

示踪弹是一个端到端行为切片。它证明路径工作，教你关于界面的知识，并保持每个下一个测试基于你刚刚学到的东西。

### 为什么顺序重要

**"我会在之后写测试来验证它工作"**

在代码之后写的测试立即通过。立即通过什么都不证明：
- 可能测试错误的东西
- 可能测试实现，不是行为
- 可能忘记边界情况
- 你从未看到它捕获 bug

测试优先强制你看到测试失败，证明它实际测试了什么。

**"我已经手动测试了所有边界情况"**

手动测试是临时的。你认为你测试了所有东西但是：
- 没有记录你测试了什么
- 代码更改时不能重新运行
- 压力下容易忘记情况
- "我尝试时它工作" ≠ 全面

自动化测试是系统的。它们每次都以相同方式运行。

**"删除 X 小时的工作是浪费"**

沉没成本谬误。时间已经过去了。你现在的选择：
- 删除并用 TDD 重写（高信心）
- 保留它并在之后添加测试（低信心，可能有 bug）

"浪费"是保留你不能信任的代码。

**"TDD 是教条的，务实意味着适应"**

TDD 是务实的：
- 在提交前发现 bug（比之后调试更快）
- 防止回归（测试立即捕获破坏）
- 记录行为（测试展示如何使用代码）
- 启用重构（自由更改，测试捕获破坏）

"务实"的捷径 = 生产中调试 = 更慢。

**"之后的测试达到相同目标——是精神不是仪式"**

不。之后的测试回答"这做什么？"之前的测试回答"这应该做什么？"

之后的测试被你的实现偏见。你测试你构建的，不是要求的。之前的测试强制在实现前发现边界情况。

### 常见合理化

| 借口 | 现实 |
|------|------|
| "太简单不需要测试" | 简单代码会坏。测试需要 30 秒。 |
| "我会在之后测试" | 立即通过的测试什么都不证明。 |
| "之后的测试达到相同目标" | 之后的测试 = "这做什么？" 之前的测试 = "这应该做什么？" |
| "已经手动测试" | 临时 ≠ 系统。没有记录，不能重新运行。 |
| "删除 X 小时是浪费" | 沉没成本谬误。保留未验证的代码是技术债。 |
| "保留作为参考，先写测试" | 你会适应它。那是之后的测试。删除就是删除。 |
| "需要先探索" | 好的。丢弃探索，从 TDD 开始。 |
| "测试困难 = 设计不清晰" | 听测试的话。难测试 = 难使用。 |
| "TDD 会让我慢下来" | TDD 比调试更快。务实 = 测试优先。 |
| "手动测试更快" | 手动不证明边界情况。你会每次更改都重新测试。 |
| "现有代码没有测试" | 你在改进它。为你接触的代码添加测试。 |

### 红旗——停下并重新开始

如果你发现自己在做以下任何事，删除代码并用 TDD 重新开始：

- 测试前的代码
- 实现后的测试
- 测试在第一次运行时立即通过
- 不能解释为什么测试失败
- "之后"添加的测试
- 合理化"就这一次"
- "我已经手动测试了"
- "之后的测试达到相同目的"
- "保留作为参考"或"适应现有代码"
- "已经花了 X 小时，删除是浪费"
- "TDD 是教条的，我是务实的"
- "这不同因为..."

**所有这些都意味着：删除代码。用 TDD 重新开始。**

## 二、接缝测试

### 什么是好测试

测试通过公共界面验证行为，不是实现细节。代码可以完全更改；测试不应该。好测试读起来像规格——"用户可以用有效购物车结账"告诉你确切存在什么能力——并且在重构后存活，因为它不关心内部结构。

### 接缝——测试位置

**接缝**是你测试的公共边界：你观察行为而不深入内部的界面。测试存在于接缝处，永不对抗内部。

**只在预先同意的接缝处测试。** 在写任何测试之前，写下测试下的接缝并与用户确认。没有在未确认接缝处写的测试。你不能测试所有东西——预先同意接缝是测试努力落在关键路径和复杂逻辑上而不是每个边界情况的方式。

问："公共界面是什么，我们应该测试哪些接缝？"

### 反模式

- **实现耦合** — mocks 内部协作者，测试私有方法，或通过侧通道验证（查询数据库而不是使用界面）。标志：当你重构但行为没有更改时测试坏掉。
- **同义反复** — 断言以代码的方式重新计算预期值（`expect(add(a, b)).toBe(a + b)`，手动以相同方式派生的快照，断言等于自身的常量），所以它通过构造并且永远不能与代码不同。预期值必须来自独立的事实来源——已知好的字面量，工作示例，规格。
- **水平切片** — 先写所有测试，然后所有实现。批量测试验证*想象的*行为：你测试事物的*形状*而不是用户面对的行为，测试对真实更改不敏感，你在理解实现之前提交测试结构。改为使用**垂直切片**——一个测试 → 一个实现 → 重复，每个测试是一个**示踪弹**，响应上一个循环教你的东西。

## 三、工作流编排

### 闭环流程

#### Phase 1: RED — 先写测试（应 FAIL）

```
1. 识别待测行为/边界条件
2. 编写最小化测试用例（仅覆盖核心逻辑）
3. 运行测试 → 确认 FAIL（证明测试有效）
4. 记录测试失败原因（预期内：功能未实现）
```

#### Phase 2: GREEN — 最小实现（应 PASS）

```
1. 编写最少量的实现代码使测试通过
2. 不添加额外功能、不做优化
3. 运行测试 → 确认 PASS
4. 检查覆盖率是否 ≥80%
```

#### Phase 3: REFACTOR — 重构优化

```
1. 在测试保护下重构代码（函数<50行，文件<800行）
2. 消除重复、提升可读性
3. 运行全部测试 → 确认仍 PASS
4. 验证覆盖率维持 ≥80%
```

### Agent 编排映射

| TDD 阶段 | 对应 Agent | 执行模式 |
|----------|-----------|---------|
| RED (写测试) | tdd-guide | 串行 |
| GREEN (最小实现) | tdd-guide | 串行 |
| REFACTOR (重构) | refactor-cleaner | 串行 |
| 完成后审查 | code-reviewer + security-reviewer | **并行** |

### 主动触发规则

```
用户提出需求
    ↓
判断：是否涉及功能/逻辑变更？
    ├─ 否 → 直接执行（文档/配置/格式）
    └─ 是 → 进入 TDD 闭环
        ↓
planner agent 拆解任务（复杂场景）
        ↓
RED → GREEN → REFACTOR
        ↓
code-reviewer + security-reviewer 并行审查
        ↓
conventional commit (feat/fix/refactor)
```

### 硬性约束

- 测试覆盖率 ≥80%（单位+集成+E2E）
- 函数 <50 行，文件 <800 行
- 嵌套 ≤4 层
- 按功能/领域组织文件
- Schema-based 输入校验，快速失败

### 与哲学的映射

TDD 闭环是"感知→判断→干预"循环的工程实现：
- **RED** = 感知（定义期望行为）
- **GREEN** = 判断（最小化实现满足期望）
- **REFACTOR** = 干预（优化结构保持行为不变）

这与 Teleological Agent → Mechanistic Mirror 模型完全同构。

## 四、Hermes Agent 集成

### 运行测试

使用 `terminal` 工具在每个步骤运行测试：

```python
# RED — 验证失败
terminal("pytest tests/test_feature.py::test_name -v")

# GREEN — 验证通过
terminal("pytest tests/test_feature.py::test_name -v")

# 完整套件 — 验证无回归
terminal("pytest tests/ -q")
```

### 与 delegate_task 一起使用

当为实现分派子代理时，在目标中强制 TDD：

```python
delegate_task(
    goal="Implement [feature] using strict TDD",
    context="""
    Follow test-driven-development skill:
    1. Write failing test FIRST
    2. Run test to verify it fails
    3. Write minimal code to pass
    4. Run test to verify it passes
    5. Refactor if needed
    6. Commit

    Project test command: pytest tests/ -q
    Project structure: [describe relevant files]
    """,
    toolsets=['terminal', 'file']
)
```

### 与 systematic-debugging 一起使用

发现 bug？写失败测试复现它。遵循 TDD 循环。测试证明修复并防止回归。

永远不要在没有测试的情况下修复 bug。

## 五、验证清单

在标记工作完成之前：

- [ ] 每个新函数/方法都有测试
- [ ] 在实现前看到每个测试失败
- [ ] 每个测试因预期原因失败（功能缺失，不是拼写错误）
- [ ] 为每个测试写最小代码通过
- [ ] 所有测试通过
- [ ] 输出干净（没有错误、警告）
- [ ] 测试使用真实代码（只在不可避免时使用 mocks）
- [ ] 边界情况和错误覆盖

不能检查所有框？你跳过了 TDD。重新开始。

## 六、卡住时

| 问题 | 解决方案 |
|------|---------|
| 不知道如何测试 | 写期望的 API。先写断言。问用户。 |
| 测试太复杂 | 设计太复杂。简化界面。 |
| 必须 mock 所有东西 | 代码太耦合。使用依赖注入。 |
| 测试设置巨大 | 提取助手。仍然复杂？简化设计。 |

## 七、测试反模式

- **测试 mock 行为而不是真实行为** — mocks 应该验证交互，不是替换被测系统
- **测试实现细节** — 测试行为/结果，不是内部方法调用
- **只有快乐路径** — 总是测试边界情况、错误和边界
- **脆弱测试** — 测试应该验证行为，不是结构；重构不应该破坏它们

## 八、最终规则

```
生产代码 → 测试存在并且先失败
否则 → 不是 TDD
```

没有用户明确许可的例外。
